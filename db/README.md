# ฐานข้อมูลและระบบล็อกอิน — NP Taskwork

ฐานข้อมูล PostgreSQL (ออกแบบมาสำหรับ Supabase) แปลงจากโครงสร้างข้อมูลใน
`src/types.ts` และ `src/data/mockData.ts` ที่เดิมเก็บอยู่ใน localStorage

## ไฟล์ในโฟลเดอร์นี้ (รันตามลำดับเลข)

| ไฟล์ | เนื้อหา |
|---|---|
> **อัปเดตแล้วเคยรันไปก่อนหน้านี้?** `02_views_functions.sql` มีการแก้ (เพิ่มคอลัมน์
> `created_by_user_id` กับ `last_inactivity_alert_at` ใน `v_tasks` และเพิ่มพารามิเตอร์ผู้ลงมือ
> ให้ `app_apply_flow_template`) ต้องรันไฟล์นี้ซ้ำอีกครั้ง ไม่งั้นหน้าเว็บจะโหลดงานไม่ขึ้น

| `01_schema.sql` | Extension, Enum 10 ชุด, ตาราง 12 ตาราง, Foreign key, Index 58 ตัว, Trigger |
| `02_views_functions.sql` | ฟังก์ชันงานหลัก (SLA, เปลี่ยนสถานะงาน) + View รายงาน 8 ตัว |
| `03_rls.sql` | Row Level Security แยกสิทธิ์ user / admin / super_admin |
| `04_seed.sql` | ข้อมูลตัวอย่าง (ผู้ใช้ 6, โครงการ 10, งาน 6 ใบครบทุกสถานะ) — ข้ามได้ถ้าใช้งานจริง |

| `06_patch_notifications.sql` | เปิดให้ผู้เกี่ยวข้องกับงานส่งแจ้งเตือนหากันได้ (ไม่ใช่แค่ admin) — รันซ้ำได้ |
| `07_line_integration.sql` | แจ้งเตือนเข้ากลุ่ม LINE — ตาราง `line_config` / `line_outbox`, trigger งานตีกลับ, ข้อความสรุปรายวัน — รันซ้ำได้ |

| `10_task_code.sql` | ออกรหัสการ์ดงานจากฝั่งฐานข้อมูล (`#NP-MM/YY-NNN` เริ่มนับใหม่ทุกเดือน) แก้ปัญหารหัสซ้ำเมื่อหลายคนสร้างพร้อมกัน — รันซ้ำได้ |

### 2. รันไฟล์ SQL

เปิด **SQL Editor** ในหน้า Dashboard แล้ววางเนื้อหาทีละไฟล์ตามลำดับ กด Run ทีละไฟล์

หรือถ้าถนัด command line:

```bash
psql "postgresql://postgres:[รหัสผ่าน]@db.[project-ref].supabase.co:5432/postgres" \
  -f db/01_schema.sql \
  -f db/02_views_functions.sql \
  -f db/03_rls.sql \
  -f db/04_seed.sql \
  -f db/05_auth.sql \
  -f db/06_patch_notifications.sql \
  -f db/07_line_integration.sql \
  -f db/09_line_cleanup.sql \
  -f db/10_task_code.sql \
  -f db/11_task_delete_cascade.sql \
  -f db/12_task_deletion_log.sql
```

> **`11` กับ `12` ต้องมาคู่กัน** — `11` เปิดให้ลบการ์ดงานได้ ส่วน `12` คือตัวที่บันทึกว่าใครลบ
> ถ้ารันแค่ `11` ระบบจะลบงานได้โดยไม่เหลือหลักฐานเลย และถ้าอัปหน้าเว็บก่อนรัน `12`
> หน้า Audit Log จะไม่มีแท็บประวัติการลบให้ดู (แต่ส่วนอื่นของระบบยังทำงานปกติ)

> ถ้าใช้งานจริง (ไม่ต้องการข้อมูลตัวอย่าง) ให้ข้าม `04_seed.sql`

> **ห้ามลืม `06` / `07`** — ถ้ารันแค่ถึง `05` ระบบจะไม่มีตาราง `line_config` และ
> `line_outbox` เลย หน้าเว็บจะอ่านค่าไม่ได้แล้วแสดงสวิตช์ LINE เป็น "ปิด" ตลอดไป
> โดยไม่มี error ให้เห็น

> **`08_line_schedule.sql` ไม่ได้อยู่ในคำสั่งข้างบนโดยตั้งใจ** — ต้องแก้ `[PROJECT_REF]`
> ในไฟล์และเก็บ secret ลง Vault ก่อน (ดูหัวไฟล์) ถ้ายังไม่ได้ตั้ง secret ไฟล์จะหยุด
> พร้อมข้อความบอกทันที

> **`09_line_cleanup.sql` รันได้ก็ต่อเมื่อ deploy แอปเวอร์ชันใหม่ไปแล้ว** เพราะมันลบ
> คอลัมน์ `line_notify_token` / `line_notify_enabled` ที่แอปเวอร์ชันเก่ายังอ่านอยู่
> (ติดตั้งใหม่ทั้งระบบรันต่อได้เลย เพราะยังไม่มีแอปเวอร์ชันเก่าให้พัง)

> ⚠️ **รัน `03_rls.sql` เมื่อไหร่ ต้องรัน `07_line_integration.sql` ต่อท้ายทุกครั้ง**
>
> `03` มีคำสั่ง `grant execute on all functions in schema public to authenticated`
> แบบเหวี่ยงแห ซึ่งคืนสิทธิ์ให้ฟังก์ชันที่ `07` ตั้งใจปิดไว้ (`app_claim_line_outbox`,
> `app_build_line_digest`, `app_enqueue_line_digest`) ตัวที่อันตรายที่สุดคือ
> `app_claim_line_outbox` — เป็น `security definer` คืนเนื้อความทุกข้อความที่รอส่ง
> และบวก `attempts` ให้ทุกแถวที่ดึงมา ผู้ใช้ที่ล็อกอินคนไหนก็ได้เรียกผ่าน PostgREST
> 5 ครั้งก็ดันทุกแถวเลยเพดาน = ช่องทางแจ้งเตือน LINE เงียบทั้งระบบ
>
> ท้ายไฟล์ `03` มีบล็อก `do $$ ... $$` ปิดคืนให้อัตโนมัติแล้ว (ข้ามเองถ้ายังไม่ได้รัน `07`)
> แต่การรัน `07` ต่อท้ายเป็นการยืนยันที่แน่นอนที่สุด ตรวจผลได้ด้วย
>
> ```sql
> select has_function_privilege('authenticated', 'app_claim_line_outbox(integer)', 'execute');
> -- ต้องได้ false
> ```
>
> หมายเหตุ: ปัจจุบัน `03_rls.sql` ยัง**รันซ้ำบนฐานข้อมูลเดิมตรง ๆ ไม่ได้** — มันจะหยุดที่
> `create trigger users_guard_privileged_columns` ว่ามีอยู่แล้ว และเพราะทั้งไฟล์อยู่ใน
> ทรานแซกชันเดียว ผลคือไม่มีอะไรเปลี่ยนเลย ถ้าจำเป็นต้องรันซ้ำจริง ให้ `drop trigger`
> และ `drop policy` ตัวที่ซ้ำก่อน แล้วอย่าลืมรัน `07` ต่อท้ายตามข้างบน

## ระบบล็อกอินทำงานอย่างไร

```
สมัครใหม่ผ่านหน้าเว็บ
  └─> Supabase Auth สร้างบัญชีใน auth.users (ดูแลอีเมล/รหัสผ่าน/session)
       └─> trigger on_auth_user_created ทำงาน
            ├─ อีเมลตรงกับโปรไฟล์เดิมที่มีอยู่ -> ผูกเข้ากับโปรไฟล์เดิม (งานเก่าไม่หลุด)
            ├─ เป็นคนแรกของระบบ            -> super_admin + อนุมัติทันที
            └─ นอกนั้น                      -> สร้างโปรไฟล์ใหม่สถานะ pending + แจ้ง admin
```

ตาราง `public.users` เก็บโปรไฟล์ในระบบงาน ผูกกับบัญชีล็อกอินด้วยคอลัมน์ `auth_user_id`
รหัสผ่านไม่ได้เก็บในตารางนี้ — อยู่ในความดูแลของ Supabase Auth ทั้งหมด

### สิทธิ์การเข้าถึงข้อมูล (RLS)

| บทบาท | สิทธิ์ |
|---|---|
| ยังไม่ล็อกอิน | ไม่เห็นข้อมูลใด ๆ |
| `pending` / `rejected` | เห็นได้แค่โปรไฟล์ตัวเอง (เพื่อแสดงหน้ารออนุมัติ) |
| `user` | อ่านงานทั้งทีมได้ แต่แก้ได้เฉพาะงานที่ตัวเองเป็นเจ้าของ/ผู้รับงาน/ผู้ตรวจ |
| `admin` | จัดการงานและโครงการทั้งหมด อนุมัติ/ตีกลับงาน อนุมัติผู้ใช้ |
| `super_admin` | สิทธิ์ของ admin + เปลี่ยน role และลบผู้ใช้ |

ข้อจำกัดที่บังคับในระดับฐานข้อมูล (แก้ที่หน้าเว็บอย่างเดียวไม่พอ):

- ผู้ใช้ทั่วไปแก้ `role`, `status`, `auth_user_id` ของตัวเองไม่ได้
- เฉพาะ `super_admin` เท่านั้นที่แต่งตั้ง admin ได้
- ข้อมูลการเงิน (`task_financials`) เห็นได้เฉพาะผู้ที่เกี่ยวข้องกับงานนั้นและ admin
- `task_logs` เป็น append-only — แก้หรือลบประวัติย้อนหลังไม่ได้ แม้แต่ระดับฐานข้อมูล
  ยกเว้นกรณีเดียวคือถูกลบตามการ์ดงานแม่ที่แอดมินสั่งลบ (`on delete cascade` ดู `11_task_delete_cascade.sql`)
- `task_deletion_log` เป็น append-only แบบไม่มีข้อยกเว้น — ห้าม UPDATE/DELETE ทุกกรณี
  ทุกครั้งที่การ์ดงานถูกลบจะมีแถวบันทึกไว้เสมอ รวมถึงตอนลบจาก SQL Editor (จะระบุว่าไม่ทราบผู้ลบ)

## ฟังก์ชันที่เรียกใช้ได้จากแอป

| ฟังก์ชัน | ใช้ทำอะไร |
|---|---|
| `app_change_task_status(task_id, สถานะใหม่, คอมเมนต์, ทำแทนใคร)` | เปลี่ยนสถานะงาน + เขียน audit log + ยิงแจ้งเตือน ในทรานแซกชันเดียว |
| `app_approve_user(user_id, อนุมัติ?)` | อนุมัติ/ปฏิเสธคำขอสมัคร (หน้าเว็บเรียกให้อัตโนมัติแล้ว) |
| `app_apply_flow_template(task_id, template_id, ทับของเดิม?)` | เติม checklist จากเทมเพลต Flow |
| `app_refresh_sla_statuses()` | คำนวณสถานะ SLA ใหม่ทั้งระบบ — ควรตั้ง cron รันทุกชั่วโมง |
| `app_my_profile()` | โปรไฟล์ของผู้ที่ล็อกอินอยู่ |
| `app_pending_users()` | รายชื่อคำขอที่รออนุมัติ (เฉพาะ admin) |

ตัวอย่างการเรียกจากฝั่งหน้าเว็บ:

```ts
const { data, error } = await supabase.rpc('app_change_task_status', {
  p_task_id: taskId,
  p_new_status: 'pending_review',
  p_comment: 'ทดสอบระบบเรียบร้อย แนบไฟล์รายงานแล้ว',
  p_on_behalf_of_user_id: null,   // ใส่ id เมื่อทำแทนคนอื่น
});
```

ตั้ง cron ให้คำนวณ SLA อัตโนมัติ (Dashboard > Database > Extensions เปิด `pg_cron` ก่อน):

```sql
select cron.schedule('refresh-sla', '0 * * * *', 'select app_refresh_sla_statuses()');
```

## แอปอ่าน/เขียนฐานข้อมูลอย่างไร

ตั้งแต่เวอร์ชันนี้ **แอปไม่ใช้ localStorage แล้ว** ข้อมูลทุกอย่างอยู่บนฐานข้อมูล
ถ้าไม่ได้ตั้งค่า `.env.local` จะเข้าใช้งานไม่ได้เลย (ไม่มีโหมดสาธิตแล้ว)

| ไฟล์ | หน้าที่ |
|---|---|
| `src/lib/supabase.ts` | สร้าง client และเก็บ session |
| `src/lib/api.ts` | แปลงข้อมูล DB (snake_case) ↔ type ฝั่งแอป (camelCase) + query/mutation ทั้งหมด |
| `src/context/AuthContext.tsx` | ล็อกอิน/สมัคร/ออกจากระบบ และโปรไฟล์ปัจจุบัน |
| `src/context/AppContext.tsx` | ถือ state ของทั้งแอป โหลดครั้งแรกทีเดียวแล้ว refresh เฉพาะส่วนที่แก้ |

หลักการ: อ่านงานทั้งกระดานจาก `v_tasks` (ได้ชื่อโครงการ/ผู้รับผิดชอบและ SLA สดมาพร้อมกัน)
แล้วดึงตารางลูก (รายการตรวจ งวดงาน จุดมาร์ก ไฟล์แนบ การเงิน) มาประกอบฝั่งหน้าเว็บ
เมื่อแก้ไขงานใบใดใบหนึ่ง จะโหลดใหม่เฉพาะใบนั้นด้วย `fetchTask()` ไม่ดึงใหม่ทั้งกระดาน

การเปลี่ยนสถานะงานทุกครั้งวิ่งผ่าน `app_change_task_status()` เสมอ เพื่อให้การอัปเดตสถานะ
การเขียน audit log และการแจ้งเตือน เกิดขึ้นพร้อมกันในทรานแซกชันเดียว — ไม่มีทางที่สถานะจะ
เปลี่ยนแล้วประวัติหาย

## ย้ายข้อมูลเดิมจาก localStorage (ถ้าเคยใช้เวอร์ชันก่อนหน้า)

ถ้าเคยกรอกงานจริงไว้ในเบราว์เซอร์ก่อนเปลี่ยนมาใช้ฐานข้อมูล

1. เปิดเวอร์ชันเก่า กด **สำรองข้อมูล & Data Policy** เพื่อ export ไฟล์ JSON เก็บไว้
2. รัน `01`, `02`, `03`, `05` บนโปรเจกต์ Supabase (**ข้าม** `04_seed.sql`)
3. นำเข้าข้อมูลจาก JSON โดยแมปตามนี้ และใส่ id เดิมลงคอลัมน์ `legacy_id` ทุกตาราง
   เพื่อให้ความสัมพันธ์ระหว่างตารางยังตรงกัน

   | JSON เดิม | ตารางปลายทาง |
   |---|---|
   | `users[]` | `users` |
   | `projects[]` | `projects` |
   | `tasks[]` | `tasks` + `task_checklist_items` + `task_milestones` + `task_annotations` + `attachments` |
   | `logs[]` | `task_logs` |
   | `notifications[]` | `notifications` |
   | `flowTemplates[]` | `flow_templates` + `flow_template_items` |

4. ให้ผู้ใช้แต่ละคนสมัครด้วย**อีเมลเดิมที่อยู่ในระบบ** — trigger จะผูกบัญชีล็อกอิน
   เข้ากับโปรไฟล์เดิมให้เอง งานเก่าทั้งหมดจึงยังอยู่กับเจ้าของเดิม

> `04_seed.sql` เป็นตัวอย่างการเขียน INSERT ที่อ้างอิงกันด้วย `legacy_id` ใช้ดูเป็นแบบได้

## หมายเหตุการออกแบบ

- **ตัดฟิลด์ชื่อซ้ำซ้อนออก** — เดิม `Task` เก็บทั้ง `projectId` และ `projectName`
  (รวมถึงชื่อผู้รับผิดชอบ/ผู้ตรวจ) ในฐานข้อมูลเก็บแค่ id แล้ว join เอาชื่อจาก
  `v_tasks` แทน ชื่อจึงไม่มีวันหลุด sync เวลาแก้ข้อมูลผู้ใช้
- **ยกเว้น `task_logs`** ที่ยังเก็บ snapshot ชื่อไว้ด้วย เพราะเป็นหลักฐานย้อนหลัง
  ชื่อ ณ เวลาที่บันทึกต้องไม่เปลี่ยนตามภายหลัง
- **`last_updated_at` ขยับเฉพาะตอนเนื้องานเปลี่ยนจริง** — การคำนวณ SLA ใหม่หรือ
  การยิงแจ้งเตือนไม่นับ ไม่งั้นงานที่ค้างอยู่จะดูเหมือนมีความเคลื่อนไหวตลอดเวลา
- **`remaining_balance` เป็น generated column** คำนวณจาก
  ยอดงวดสัญญา − (ค่าตอบแทน + ค่าวัสดุ + ค่าใช้สอย) แก้มือให้ผิดไม่ได้
- **สถานะงานเปลี่ยนได้เฉพาะเส้นทางที่ถูกต้อง** เช่น ข้ามจาก "รอส่งงาน" ไป
  "อนุมัติ" เลยไม่ได้ และเฉพาะ admin เท่านั้นที่อนุมัติหรือตีกลับได้
